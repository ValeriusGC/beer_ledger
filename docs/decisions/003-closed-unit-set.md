# ADR 003: замкнутый набор единиц измерения и хранение факта в базовой единице

**Дата создания:** 2026-07-28 16:06 +0500  
**Последнее обновление:** 2026-07-28 16:06 +0500  
**Версия:** 1  
**Вид документа:** ADR

**Статус:** Accepted  
**Итерация:** 1.1 (core), последствия — в 2 (persistence)

> Набор единиц измерения фиксирует разработчик. Пользовательская «кружка 0.33» — это пресет кликера, а не новая единица. В записи тапа хранится факт в базовой единице семейства; единица ввода хранится рядом и служит только для отображения.

Связанные документы: [ADR 002](./002-domain-style.md) · [architecture.md](../architecture.md)

---

## Контекст

Решение о форме `MeasureUnit` (ADR 002 §4) выбрало enum, а enum — **замкнутый** набор. Отсюда вопрос, который надо закрыть до проектирования схемы БД: сможет ли пользователь заводить свои единицы измерения?

Вопрос не косметический. Открытый набор означает, что коэффициент единицы — пользовательские данные, а значит он **изменяем во времени**, и это напрямую определяет, что именно лежит в записи тапа.

---

## Решение

### 1. Набор единиц замкнут

Единицы измерения задаёт разработчик; в приложении их нельзя ни добавить, ни отредактировать.

Причина не в стоимости реализации, а в границе понятий. **Единица измерения — это масштаб оси**: замкнутая физика, где литр, миллилитр и пинта связаны неизменными коэффициентами. А «кружка 0.33» — это **именованное значение в литрах**, то есть свойство кликера, а не новая точка на шкале. Пользователю, который хочет учитывать свою кружку, нужен кликер с объёмом `0.33 L` — и это уже запланированный пресет (`beerHalfLiter` в PR 6), а не запись в реестре единиц.

Открытый набор понадобился бы только для другого желания: чтобы **итог за период** отображался «в кружках», то есть чтобы кружка стала масштабом оси, а не размером порции. Это существенно более редкий сценарий, и он не входит в v1 — см. `project_pivomer/deferred-decisions.md` в штабе.

### 2. В записи тапа — факт в базовой единице семейства

`Click` хранит значение, приведённое к базовой единице (объём — в миллилитрах, деньги — в копейках, энергия — в калориях). Единица, в которой пользователь **вводил** значение, хранится рядом как `id` и используется только для отображения.

```dart
// Иллюстрация формы, не финальный API (модели — PR 4)
Click(
  volumeBase: 500,             // мл — факт, не пересчитывается никогда
  volumeEnteredIn: 'volume.liter', // как показывать: «0.5 L»
);
```

Причина — прошлое не должно меняться от правки кода или настроек. Доказательство из этой же итерации: при переносе из `fast_2020` пинта США была исправлена с округлённых `470` мл на точные `473.176473`. Если бы тап хранил «1 pintUs» и объём вычислялся при чтении, все исторические записи молча сдвинулись бы на 0.7 %. То же произойдёт при любом будущем уточнении коэффициента или при появлении редактируемых пользовательских единиц.

Побочные выгоды: агрегация за период суммирует числа в общей базе без конвертации, а экспорт данных остаётся самодостаточным — файл не обязан нести определения единиц.

### 3. Хранить `id`, не `name` и не `index`

`index` ломается от перестановки значений enum, `name` — от переименования идентификатора в Dart. Формат хранения — только `MeasureUnit.id` (`volume.liter`), и он закреплён golden-тестом `test/measure/measure_wire_format_test.dart`: изменение идентификатора роняет тест и требует осознанного подтверждения вместе с миграцией.

Это то же соглашение, что `@JsonValue` в `json_serializable`, только id живёт полем enum'а и не требует codegen в core.

## Альтернативы

### A. Открытый набор: `CustomUnit` рядом с enum-семействами

Интерфейс `MeasureUnit` это допускает — достаточно класса с валидирующей фабрикой:

```dart
final class CustomUnit implements MeasureUnit {
  static Result<CustomUnit> create({...});  // отвергает ratio <= 0, NaN, Infinity
}
```

**Плюсы:** «итог в кружках»; на уровне типов почти бесплатно (потеря исчерпывающего `switch` не важна — конвертация это арифметика, а не разбор случаев).

**Минусы — все в жизненном цикле данных, не в типах:**

- редактирование коэффициента задним числом (решается пунктом 2 настоящего ADR, то есть частично);
- таблица `units` и решение, лежат ли в ней встроенные единицы: если да — seed и миграция на каждую новую встроенную; если нет — двухступенчатый resolve и разведение пространств id (`custom.*`);
- экспорт обязан нести определения custom-единиц, иначе файл нечитаем на другом устройстве;
- CRUD-экран, лимит количества, уникальность подписи, запрет менять `family` после создания.

**Отвергнуто для v1:** цена — недели UI-работы за сценарий, который в спеке отсутствует. Пункт 2 сохраняет опцию: добавление `CustomUnit` позже не потребует миграции истории тапов.

### B. Хранить ссылку на единицу и вычислять значение при чтении

**Минусы:** правка коэффициента переписывает историю; агрегация обязана конвертировать на каждом чтении.  
**Отвергнуто:** ровно та ошибка, которую вскрыла история с пинтой.

### C. Хранить значение в единице ввода без нормализации

**Минусы:** сумма за период требует конвертации каждой записи, а при неизвестном id единицы запись становится непригодной.  
**Отвергнуто:** база нужна для агрегации; единица ввода сохраняется дополнительно, а не вместо.

## Последствия

**Плюсы**

- История тапов неизменна при любых правках коэффициентов и кода;
- Агрегация — сложение чисел в общей базе, без конвертации;
- Экспорт самодостаточен;
- Единицы остаются enum'ами: замкнутость и полнота `switch` от языка.

**Минусы / costs**

- В `Click` два поля на ось вместо одного (факт + единица ввода);
- «Итог в кружках» невозможен без пересмотра этого ADR;
- Отображение всегда требует обратной конвертации из базы — по формуле `ratioToBase`, то есть дёшево.

**Условия пересмотра**

Возвращаемся к варианту A, если появится хотя бы одно:

1. запрос отображать итоги в пользовательской единице («12 кружек за месяц»);
2. вторая валюта в денежной оси — потребует курса и, вероятно, открытого набора;
3. вертикаль MeaTap с пользовательскими порциями как масштабом оси.

Пункт 2 настоящего ADR специально выбран так, чтобы этот пересмотр не требовал миграции существующих записей.
